# 腾讯云迁移与商家微信小程序重建设计

## 1. 目标

将当前阿里云上的文具店会员系统迁移到腾讯云 `101.35.96.147`，保留现有 Java 后端、Vue Web 端、业务规则和生产业务数据；废弃原有独立小程序后端及其独立数据模型，重新建设原生微信小程序，并让 Web 与小程序共用同一套门店、会员、钱包和交易流水。

腾讯云首发必须在没有微信支付商户号的情况下完整支持现有记账业务。真实微信支付采用“服务商 + 特约商户”模式预留，后续取得服务商号并完成真实门店入驻后按门店启用。

本文档取代根目录 `docs/superpowers/specs/2026-06-22-merchant-miniprogram-design.md` 中“独立小程序后端 + 独立数据库”的方案；旧文档只作为历史设计记录，不再作为实施依据。

## 2. 已确认约束

- 腾讯云系统为 Ubuntu 24.04，SSH Host 为 `tencent`，公网 IP 为 `101.35.96.147`。
- 数据盘为 `/dev/vdb`，ext4 文件系统，持久挂载在 `/mnt/datadisk0`。
- Java、MySQL、Redis、Nginx 软件包以及 systemd、Nginx 配置由 Ubuntu 管理。
- 应用、数据库、Redis 持久化数据、上传文件、运行配置、支付证书、发布包和备份必须放在 `/mnt/datadisk0`。
- 域名使用 `usepenciles.com`，当前尚未完成 ICP 备案。
- 迁移阿里云现有业务数据，允许最终切换时有 5 至 10 分钟维护窗口。
- 每个门店未来使用独立微信支付商户号，资金独立结算。
- 当前尚无微信支付服务商号或门店商户号，腾讯云首发必须默认采用记账模式。

## 3. 当前状态

### 3.1 阿里云生产环境

- Java 服务、MySQL、Redis、Nginx 均在运行。
- 线上后端 JAR 和前端静态文件与本地构建产物校验和一致。
- 现有业务库为 `stationery_member`，当前包含 5 个门店、7 个会员和 22 条钱包交易流水。
- 当前数据规模约 0.5 MB，上传目录约 8 KB。
- 后端使用 `8090`，Nginx 提供 Web、`/api/` 和 `/uploads/` 入口。

### 3.2 腾讯云环境

- 数据盘约 98 GB，可用约 93 GB。
- 尚未安装 Java、MySQL、Redis、Nginx。
- 当前仅开放 SSH；UFW 未启用，SSH 仍允许密码认证。

### 3.3 旧小程序实现

- `merchant-mini-backend/` 使用独立的 `mini_*` 表，会与现有 Web 业务数据形成两套账。
- `merchant-miniprogram/` 默认运行本地 mock，真实微信登录、真实支付和生产会话尚未形成可上线闭环。
- 旧小程序实现不直接部署。删除活动目录前先制作可恢复归档，随后由全新的小程序工程替代。

## 4. 总体架构

```text
Vue Web ───────────────┐
                       ├── Nginx ── Spring Boot ── MySQL
原生微信小程序 ────────┘              │
                                      ├── Redis
                                      └── 微信支付服务商 API（按配置启用）
```

- `backend/` 是唯一业务后端，继续承载管理员、商家、会员、钱包、充值、消费、退款和审计能力。
- `frontend/` 保留现有 Vue 功能和接口契约。
- 新小程序是新的客户端，不复制钱包计算、充值梯度、交易状态或权限判断。
- Web 和小程序访问同一个 `stationery_member` 数据库。
- 小程序业务接口继续使用现有 `/api/merchant/**` 能力；新增接口仅覆盖微信登录绑定、Bearer Token 和微信支付。
- 不再创建 `mini_stationery_member` 数据库，也不保留 `mini_*` 业务表。

## 5. 小程序认证

### 5.1 登录流程

1. 小程序调用 `wx.login` 获取临时 code。
2. 后端调用微信 `jscode2session` 换取 `openid`。
3. 已绑定门店时直接签发 12 小时商家 token。
4. 未绑定时，商家输入现有门店账号和密码完成一次绑定。
5. 后续请求通过 `Authorization: Bearer TOKEN_VALUE` 访问现有商家接口。

### 5.2 兼容策略

- Vue Web 继续使用现有 HttpOnly Cookie，不改变现有登录方式。
- 后端商家身份解析同时接受商家 Cookie 和 Bearer Token，两者映射到同一 `login_session` 和 `store_account`。
- 管理员接口不接受小程序 Bearer Token。
- 新增 `store_wechat_binding` 表保存 `store_id`、`openid`、绑定状态和时间；`openid` 必须唯一。
- 停用门店后，Web Cookie 和小程序 token 都立即失去业务访问权限。

## 6. 双模式微信支付

### 6.1 模式定义

平台能力由 `STATIONERY_PAYMENT_MODE` 控制：

- `BOOKKEEPING`：默认值。微信、支付宝、现金仅作为账务分类，充值沿用现有逻辑。
- `WECHAT_SERVICE_PROVIDER`：启用微信支付服务商能力，但只有门店配置为 `REAL` 且授权状态正常时才能真实收款。

每个门店具有独立的微信支付模式：

- `BOOKKEEPING`：即使平台已启用服务商能力，该门店仍执行原有记账逻辑。
- `REAL`：使用该门店的 `sub_mchid` 发起微信支付服务商 V3 Native 支付，由商家小程序展示动态收款二维码，顾客扫码付款。

门店缺少支付配置时默认 `BOOKKEEPING`。平台配置缺失时禁止把门店切换为 `REAL`。真实支付请求失败、超时或配置异常时不得静默降级为记账成功。

### 6.2 真实支付边界

- 真实微信支付仅用于会员充值收款。
- 会员消费继续从充值余额和赠送余额扣减，不额外向顾客微信扣款。
- 服务商使用统一 `sp_mchid`、API v3 密钥、商户 API 私钥和证书。
- 每个真实门店保存自己的 `sub_mchid`、授权状态和产品开通状态，资金直接结算到该门店账户。
- 服务商私钥、API v3 密钥和证书文件不得写入数据库、代码、日志或 README。
- 首发只实现真实充值收款，不把现有账务退款伪装成微信资金退款。真实支付产生的充值流水在微信退款流程完成开发和真实商户验收前禁止执行撤销/退款；记账模式原有撤销/退款规则保持不变。

### 6.3 支付数据模型

新增 `store_wechat_pay_config`：

- `store_id`：唯一关联门店。
- `payment_mode`：`BOOKKEEPING` 或 `REAL`。
- `sub_mchid`：特约商户号，记账模式允许为空。
- `authorization_status`：`PENDING`、`ENABLED`、`DISABLED`。
- `updated_at`：配置更新时间。

新增 `wechat_payment_order`：

- 平台订单号、微信支付订单号、门店、会员、充值金额、赠送金额。
- `sp_mchid`、`sub_mchid` 和下单时使用的 AppID 快照。
- 幂等 key、订单状态、失败原因、创建时间、支付时间和更新时间。
- 保存微信返回的 `code_url` 及二维码失效时间，供小程序生成动态收款二维码。
- 订单状态至少包含 `CREATED`、`WAITING_PAYMENT`、`SUCCESS`、`FAILED`、`CLOSED`。
- 平台订单号和业务幂等 key 均建立唯一约束。

### 6.4 真实支付流程

1. 商家在小程序选择会员、输入充值金额并提交幂等 key。
2. 后端校验当前门店状态、门店支付模式、服务商配置和特约商户授权状态。
3. 后端创建本地支付单，调用微信支付服务商 V3 Native 下单接口并取得 `code_url`。
4. 小程序把 `code_url` 渲染为动态收款二维码，顾客使用自己的微信扫码并完成付款。
5. 后端通过 HTTPS 异步回调接收支付结果；回调缺失或延迟时，由小程序轮询触发后端主动查询订单状态。
6. 回调必须使用原始请求体和微信支付官方 Java SDK验签、解密。
7. 仅在回调或主动查询确认微信订单为 `SUCCESS` 后，调用现有充值服务写入 `wallet_transaction` 并更新会员钱包。
8. 数据库事务和唯一约束保证同一支付单最多生成一笔成功充值流水。
9. 未支付、支付失败、关单或最终超时不得增加会员余额。

## 7. 腾讯云目录和服务

```text
/mnt/datadisk0/stationery-member/
├── backend/
├── frontend/
├── uploads/
├── releases/
├── config/
│   ├── backend.env
│   └── wechat-pay/
└── backups/

/mnt/datadisk0/mysql/
/mnt/datadisk0/redis/
```

- 后端以专用低权限用户运行，工作目录位于数据盘。
- Java 只监听 `127.0.0.1:8090`。
- MySQL 和 Redis 只监听本机，数据目录位于数据盘。
- Nginx 在备案前提供 IP HTTP 入口；备案和证书就绪后提供域名 HTTPS，并将 HTTP 重定向到 HTTPS。
- 支付配置目录权限为 `root` 管理、应用运行组只读；目录权限不高于 `750`，密钥文件权限为 `640` 或更严格。

## 8. 数据迁移

### 8.1 预部署

- 在腾讯云安装并配置 JRE 17、MySQL 8、Redis、Nginx。
- 建立数据盘目录、运行用户、服务单元和 Nginx 站点。
- 部署与阿里云线上校验和一致的 Java/Vue 版本并完成空库启动验证。

### 8.2 最终切换

1. 进入 5 至 10 分钟维护窗口，停止阿里云 Java 服务，阻止新增业务写入。
2. 在阿里云生成带时间戳的数据库备份，并记录源库表行数与业务汇总。
3. 将备份和上传目录复制到腾讯云数据盘备份目录。
4. 导入 `stationery_member`，保留业务表数据；清空 `login_session` 和 `verification_code`。
5. 同步上传目录并校正运行用户权限。
6. 校验门店、会员、钱包、充值档位、交易流水、审计数据的行数和关键金额汇总。
7. 启动腾讯云 Java 和 Nginx，执行登录、会员查询、充值、扣款、退款和静态资源冒烟验证。
8. 阿里云保留为停止写入的回滚源，不立即删除数据库或应用目录。

### 8.3 回滚

- 腾讯云验证失败时停止腾讯云入口，重新启动阿里云 Java 服务。
- 在腾讯云正式开始接受业务写入后，不允许直接回滚到旧阿里云数据库；必须先评估并回迁腾讯云新增数据。
- 切换成功后保留迁移前备份、发布包、配置快照和校验结果。

## 9. 域名和外部平台

- API、小程序请求域名和微信支付回调规划为 `https://api.usepenciles.com`。

- 微信支付真实模式需要服务商号、API v3 密钥、API 证书、平台公钥或平台证书、特约商户号、产品授权及可公网访问的 HTTPS 回调地址。

## 10. 安全处理

- 删除 README 中的小程序 AppSecret、云 AccessKey 和其他明文密钥，只保留环境变量名称和申请说明。
- 现有已暴露的小程序 AppSecret、代码上传密钥和云 AccessKey 必须在对应控制台轮换，旧值不得继续用于生产。
- 本地代码上传私钥移动到忽略目录并设置严格权限，不上传腾讯云服务器。
- 生产数据库密码、微信支付密钥和证书只保存在数据盘受限配置目录。
- 腾讯云验证密钥登录无误后关闭 SSH 密码登录；防火墙和安全组只开放 22、80、443。
- MySQL、Redis、Java 端口不对公网开放。
- 日志不得记录密码、token、动态收款链接、API v3 密钥、私钥、完整回调报文或完整手机号。

## 11. 验证与验收

### 11.1 自动化验证

- 后端现有单元测试、交易规则测试、数据库集成测试。
- 新增 Cookie/Bearer 双认证测试、微信绑定权限测试、门店隔离测试。
- `BOOKKEEPING` 模式回归现有充值、扣款、撤销和退款。
- 支付网关使用模拟实现覆盖下单成功、等待支付、查询成功、失败、重复回调和回调验签失败。
- 小程序执行静态检查、接口契约测试和核心页面交互测试。
- Vue 执行现有 Node 测试、类型检查和生产构建。

### 11.2 迁移验收

- 腾讯云源数据行数与阿里云迁移快照一致，登录会话和验证码除外。
- 会员充值余额、赠送余额、累计充值、累计赠送、累计消费和交易流水汇总一致。
- Web 管理端和商家端可在腾讯云完成核心业务闭环。
- 没有服务商号、特约商户号和支付证书时，系统以 `BOOKKEEPING` 正常运行，不能因支付 Bean 或配置缺失而启动失败。
- `BOOKKEEPING` 门店选择微信记账时，行为与迁移前一致。
- `REAL` 模式缺失必要配置时明确拒绝下单，且不写入充值流水、不改变会员余额。
- 同一真实支付成功通知重复到达时只生成一笔充值流水。
